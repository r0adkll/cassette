# 0013: Wear

Date: 2026-10-17 · Status: accepted

Milestone 2 ([roadmap](../roadmap.md)): a Wear OS app, tile and complications, fed from the phone
([0010](0010-product-details.md)). The look is iteration 5's Wear row ([0012](0012-visual-direction.md)).

## The phone is the source

The watch never scans. The phone publishes one **snapshot** to the Wear Data Layer whenever its data
changes (debounced, like the widgets): every bike with its current components and each one's latest
reading, plus the default bike's id. No history and no photos. It is JSON in a single DataItem at
`/cassette/snapshot`, versioned, and decoded leniently (unknown fields and enum values are ignored or
read as unknown), so a watch and phone a release apart still work.

The snapshot carries data, not wording: the watch words and colours it with the same summary code as the
phone (`:features:bikes:summary`), against its own clock, so "seen 3 h ago" and the 14-day stale state
stay right while the phone is away. The watch keeps no database: the Data Layer stores DataItems on the
watch, so the last snapshot is there offline.

## Refresh

Refresh on the watch sends a message (`/cassette/request-refresh`) to the phone node that has the
`cassette_phone` capability. The phone runs the same 60-second refresh as the Quick Settings tile, one at a
time whichever surface asked, inside an expedited job so the process stays up for the whole scan. Its
progress goes back as a second DataItem (`/cassette/refresh`: scanning until a time, Bluetooth not ready, or
idle), and the watch counts down locally. When no phone is reachable the watch says so instead.

## Surfaces

- **App:** bikes (each with its weakest status), then a bike: the status block and one bar per component.
  The bike screen adds a Refresh edge button, which iteration 5 didn't draw; it is the phone's one primary
  action, in Wear's usual place. Compose for Wear OS (Material 3) with Cassette's colours and Barlow, Circuit
  + Metro like the phone.
- **Tile:** the default bike: name, status icon, headline, weakest component and when it was seen, and
  Refresh. Tiles can't load fonts, so it uses the system font; colours and icons are ours.
- **Complications:** the default bike. Ranged value: the weakest component's level (or the one to charge),
  with its value and code ("78", "RD"). Short text: the status in words with the status icon. Short-text
  slots fit about seven characters, so they use the design system's status words ("GOOD", "FD LOW", "OLD";
  "CHARGE" with the component as the title) rather than iteration 5's "ALL GOOD", which faces cut off.
  Watch faces may recolour both, so the icon and words carry status. Both update when a snapshot arrives,
  and hourly so "not seen" arrives on time.

## Packaging

`:app:wear` has the phone app's application id (`com.r0adkll.cassette`, `.debug` for debug builds) and
signing key, which the Data Layer requires. It is not standalone (it needs the phone), and needs Wear OS 4
(API 33) or later. For now it is installed with adb; Drop and Play distribution come later.

## Diagnostics

The phone's Diagnostics area gets a Wear panel: watches connected and whether Cassette is installed on
them, the last snapshot published (or why it failed) and the last refresh a watch asked for. Publishes and
refresh requests go into the capture log too ([0005](0005-diagnostics.md)).

## Modules
